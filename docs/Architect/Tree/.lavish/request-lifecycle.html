Architect.Api → Architect.Service → Architect.Repository → SQL Server

What happens first when a request arrives?

The request first enters ASP.NET Core’s middleware pipeline. Middleware handles cross-cutting concerns in order; only after routing, authentication, and authorization succeed does ASP.NET Core bind input and invoke a controller. The controller then calls Service, Service calls Repository, and Repository calls SQL Server.

Key rule: request processing goes forward through middleware; the response and exceptions travel backward through the same chain.

The whole round trip at a glance

Detailed execution

Inbound path: step by step

1

Client creates the HTTP request

The browser, mobile app, integration, or Swagger sends a method, URL, headers, and optional body—for example POST /api/courses. Typical headers include Authorization: Bearer …, Content-Type: application/json, and a trace/correlation ID.

No application layer has run yet.

2

Server accepts and normalizes the connection

Kestrel receives the bytes and builds an HttpContext. If deployed behind IIS/Nginx/a load balancer, forwarded-header processing must run early so scheme, client IP, and host represent the original request—not only the proxy.

Host filtering, HTTPS redirection, and HSTS policy belong near the edge.

3

Global exception boundary wraps everything

GlobalExceptionHandling should be one of the first application middleware components. It calls the next middleware inside a try. Any unhandled exception thrown later—from auth, controller, service, repository, or SQL access—returns to this boundary.

It maps expected exceptions to safe Problem Details and hides stack traces from clients.

4

Request logging establishes observability

The logging middleware accepts or generates a correlation ID, starts a timer, and creates log context for log4net. It records method and safe path data before calling the next component; after the response returns, it records status and duration.

Do not log access tokens, passwords, cookies, connection strings, or unrestricted bodies.

5

Routing identifies the endpoint

Routing compares the HTTP method and path against controller route templates. It selects endpoint metadata such as the controller action, authorization policies, and rate-limit policy. Route constraints can reject invalid shapes such as a non-integer ID.

If nothing matches, processing ends with 404; the controller is never called.

6

Authentication establishes identity

Authentication reads the bearer token, validates its signature, issuer, audience, lifetime, and other configured requirements, then builds HttpContext.User with identity claims.

Authentication asks “who are you?” A missing/invalid credential normally leads to 401 once access is required.

7

Authorization checks permission

Authorization evaluates the selected endpoint’s role or policy requirements against the authenticated user’s claims. Coarse endpoint access happens here; resource-specific checks can also occur later in Service after loading the target record.

Known user without permission: 403. This short-circuits before controller execution.

8

Model binding creates the request DTO

ASP.NET Core takes route values, query parameters, headers, and JSON body fields and converts them into action parameters and the request DTO. JSON syntax errors, conversion failures, missing required values, and size limits are handled before useful business work starts.

Malformed or invalid input returns a consistent 400.

9

FluentValidation checks input rules

The assignment requires FluentValidation. A dedicated folder is not required: validators can later live beside their request DTOs. Rules validate input shape and simple request constraints—for example course code format or maximum title length—not database workflows.

Validation failure returns 400 with field-specific errors; Controller/Service should not run.

10

Controller receives valid, authorized input

The controller should only translate HTTP concerns: receive the request DTO and identity context, call an injected Service interface, and translate the service result into an HTTP response. It must not write SQL, enforce complex workflows, or return persistence entities.

Example intent: ICourseService.CreateAsync(request, actor, ct).

11

Service executes the use case

The Service layer applies business rules, resource-level authorization, normalization, and transaction orchestration. It may check uniqueness, registration periods, role relationships, or soft-deleted state by calling repository interfaces.

Service knows the business operation—not HTTP and not SQL syntax.

12

Repository executes parameterized persistence

The repository converts the Service request into database operations, obtains a SQL Server connection, supplies values as parameters, enforces active-record filtering such as isDelete = 0, and passes the cancellation token where supported.

Never concatenate untrusted request values into SQL. Parameterization protects values; allow-list any dynamic column/order identifiers.

13

SQL Server performs the operation

SQL Server parses/optimizes the parameterized command, uses constraints and indexes, reads or modifies rows, and returns rows/affected count or a database error. Database constraints remain the final integrity boundary even when Service already checked a rule. A transaction commits all related changes together or rolls them back together.

Query success
Rows return to Repository.
Constraint conflict
Mapped to a safe conflict result, usually 409.
Timeout/unavailable
Logged with internal details; client receives a safe 5xx response.

Outbound response: reverse direction

  1. Repository maps returned columns to entities/data records and closes/disposes database resources.
  2. Service interprets the result and maps only permitted fields to a response DTO.
  3. Controller chooses the HTTP result: for example 200, 201 with location, or 204.
  4. Output formatting serializes the response DTO to JSON and sets content headers.
  5. Logging middleware observes final status, bytes if available, and elapsed time.
  6. Global exception middleware sees normal completion and does nothing further—or catches a propagated failure.
  7. Kestrel/proxy sends status, headers, and body back to the client.

Recommended conceptual middleware order

This is ordering guidance, not implementation added to the repository.

Forwarded headers              // first when behind a trusted proxy
Global exception handling      // catches failures from everything below
Correlation ID + request log   // surrounds operation and measures duration
HTTPS / HSTS / host checks     // edge security
Routing                        // selects endpoint and its metadata
CORS                           // when browser cross-origin access is needed
Rate limiting                  // endpoint-aware when configured that way
Authentication                 // creates HttpContext.User
Authorization                  // enforces endpoint policy
Controller endpoint            // binding → validation → action
  → Service                    // business rules and orchestration
    → Repository               // parameterized data access
      → SQL Server             // integrity, indexes, transaction
← response unwinds in reverse
Exact placement of HTTPS, forwarded headers, CORS, and rate limiting depends on deployment. Authentication must precede authorization, and global exception handling must precede components whose exceptions it should catch.

Controller must not

  • Call SQL Server
  • Use Repository directly
  • Contain workflow rules
  • Return Entity objects
  • Leak exception details

Service must not

  • Depend on API
  • Return IActionResult
  • Read raw HTTP headers
  • Build SQL strings
  • Own transport logging

Repository must not

  • Apply HTTP status codes
  • Make role decisions
  • Run business workflows
  • Concatenate user SQL
  • Expose secrets in logs

Architecture evidence: ARCHITECTURE.md defines API → Service → Repository → SQL Server and global exception middleware. The repository is still architecture-only, so this page describes the intended lifecycle rather than existing executable behavior.

Framework guidance: current ASP.NET Core documentation (/dotnet/aspnetcore.docs) confirms middleware executes in registration order, exception handling should be early, routing precedes endpoint-aware security behavior, authentication precedes authorization, and middleware can short-circuit before a controller.
